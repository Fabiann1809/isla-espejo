# Isla Espejo — project rules

Top-down pixel-art roguelike made in **Godot 4.7 (GDScript)** by two developers. Working title: "Isla Espejo" (may change).
Game design: `docs/JUEGO.md` and task list: `docs/TAREAS.md` (both written in Spanish). **Read both before starting any task.**
Visual references: `docs/referencias/` (concept images only; they are NOT game sprites).

## Core idea (do not lose sight of it)
Temple art: `python tools/finish_temple_art.py` is the complete rebuild command. It calls the base v2 adapter, then adapts all 1989 tile roles (including stairs, bridges, ledges, mossy/lava feet and incidental backdrop art) and all 25 prop strips. Run it **after** the original temple generators, which otherwise overwrite the art. Sources and `atlas_template.png` topology masks live in `assets/art_temple_v2/`; `coverage.json` records every adapted role. Atlas coordinates, palette, footprints, animation counts and hazard phase ranges stay unchanged. `TempleShape` adds up to `Tuning.TEMPLE_LAVA_CLIFF_EXTRA_ROWS` rock rows into empty lava, stopping before walkable cells; `LavaShadows` draws their shadows between sea and rock. Floor tones, dark risers and reduced fire glare distinguish heights. Validate with temple tests and `tools/snapshot_temple.gd`.

Nico is stuck on an island that mirrors and learns from him. He crosses 3 scenarios, defeats 3 bosses (each gives a compass fragment and a skill) and goes home. Three pillars:
1. **Every run is different**: procedural maps built from hand-made rooms.
2. **Fixed skills, one per boss** (no combos for now, but keep the system data-driven so combos can be added later).
3. **The island learns**: adaptive AI in two layers — player profile (layer 1) and island reaction (layer 2). Both are mandatory.

## Workflow
1. Work on **one task at a time**, in the order of `docs/TAREAS.md`, and only on tasks assigned to you (A or B) unless told otherwise. Do not add anything that is not in the docs.
2. A task is done only when:
   - the project opens and runs with no errors in the Godot console,
   - `./tools/run_tests.sh` passes (it runs the smoke check and every `tests/test_*.gd`, and fails on non-zero exit codes, timeouts or `SCRIPT ERROR`; `./tools/run_tests.sh test_skills` runs just one). On Windows set `GODOT` to the `*_console.exe` build. Add a `tests/test_<system>.gd` for each new gameplay system; in tests never `preload` scenes or reference `class_name` types of scripts that use autoloads: load at runtime, use untyped variables, `await process_frame` first if the test touches an autoload,
   - its "Hecho cuando" criterion is verified,
   - a short explanation of what was done and why is given to the user (in Spanish).
3. If anything is ambiguous or touches the scope, **ask the user** before assuming. Never expand the scope: anything marked as out of scope or as an extra in the docs is not built unless the user says so.
4. Never break what already works. If a change could affect another system, run the project and check that system before committing.

## Git and collaboration
5. Work directly on `main` and push to it (no pull requests needed). Before every push: `git pull --rebase`, run the project, and run `./tools/run_tests.sh` (must pass). Never push something that does not open or breaks what already worked. CI (`godot-check`) runs on every push; if it fails, fix it first.
   - Optional: use a short-lived branch `feature/<short-name>` for a big or risky change, then merge it into `main`.
6. One commit per task or fix. Tick the task checkbox (`[x]`) in `docs/TAREAS.md` in the same commit.
7. Commit format: [Conventional Commits](https://www.conventionalcommits.org/) in English: `type(scope): imperative summary`.
   - Types: `feat`, `fix`, `refactor`, `test`, `docs`, `build`, `chore`, `style`.
   - Scopes: `player`, `combat`, `skills`, `enemies`, `bosses`, `world`, `ai`, `npc`, `dialogue`, `ui`, `audio`, `art`, `save`, `ci`.
   - Summary ≤ 72 chars, imperative, no trailing period. Example: `feat(player): add dash with cooldown`.
8. Each person commits with **their own name and email**. **Never** add `Co-Authored-By` trailers or any AI/tool attribution to commits, PRs or files.
9. Avoid merge conflicts in Godot: do not edit a `.tscn` scene that the other person is currently working on, and `git pull --rebase` often. Shared files (`project.godot`, autoloads, `data/`) are changed in small commits, announced first. Prefer many small scenes over one big scene.
10. Releases: pushing a tag `v*` publishes a public GitHub Release (CD). Never create or push tags unless the user explicitly asks. Never commit: `.godot/`, builds, secrets, personal files, or huge unused assets. Never force-push to shared branches.

## Code
11. Everything in **English** (identifiers, comments, commits, filenames) **except player-facing text** (dialogues, UI, item names), which is **Spanish** and lives in `data/` files, never hardcoded in scripts.
12. GDScript style: `snake_case` for files, variables and functions; `PascalCase` for classes and nodes; static typing everywhere possible (`var hp: int = 10`); small functions; comment only the non-obvious "why".
13. Structure: one scene per entity and one script per scene.
    - `scenes/` (player, enemies, bosses, npcs, levels, ui), `scripts/` (same subfolders plus `skills/`, `ai/`, `world/`), `assets/` (`sprites/`, `tilesets/`, `audio/`), `data/` (JSON/Resources), `tests/`.
14. Game data is data, not code: skills, enemies, rooms and dialogues are defined in `data/` (JSON or Godot Resources) and read by generic systems. Adding a new enemy or skill must not require changing the core systems.
15. The adaptive AI lives in `scripts/ai/` and is separated from combat code. Combat code only **emits events** (e.g. "player dashed", "player hit enemy", "enemy detected player"); the AI listens. Use signals or a small event bus autoload.
16. The player profile is saved to `user://profile.json`. Keep the format versioned (`"version": 1`).
17. Resolution is 480x270 (camera zoom 1) with integer scaling and *nearest* filtering. Do not change display settings without asking.
18. Combat uses the reusable components in `scripts/components/`: `HealthComponent` (health), `Hitbox` (deals damage, once per activation) and `Hurtbox` (receives damage). Never write ad-hoc damage code; a new enemy or trap reuses them.
    - Hitboxes and hurtboxes are `Area2D` nodes. Keep `monitorable = true` on them (turning it off makes the area blind).
    - Collision layers (named in `project.godot`): 1 `world`, 2 `player` (body + Hurtbox), 3 `enemy` (body + Hurtbox), 4 `player_attack`, 5 `enemy_attack`, 7 `water` (ponds), 8 `block_low`, 9 `block_high`, 10 `block_top`, 11 `cliff_top` (height levels, below). Player Hitbox: layer 4, mask 3. Enemy/trap Hitbox: layer 5, mask 2.
    - Bodies only collide with `world` and `water` (and the player body also with `enemy`); projectiles only stop at `world`, so they fly over ponds (`tests/test_water.gd`). Damage is decided only by Hitbox vs Hurtbox.
    - Combat code publishes what happens on the `Events` autoload (`scripts/core/events.gd`); the AI and HUD listen there. Add a signal there when a new gameplay fact must be observable.
    - **Enemies**: inherit `scenes/enemies/enemy.tscn` (see `grunt.tscn`), create an `EnemyData` `.tres` in `data/enemies/` and set it as `data`. Only override the `_process_*` / `_start_attack` hooks of `scripts/enemies/enemy.gd` (in a script extending `Enemy`) when the behaviour differs. Never copy `enemy.gd`. The AI director tunes enemies through the `*_multiplier` properties before adding them to the tree.
    - **Maps** (`scripts/world/`): a scenario is a `ScenarioData` (`data/scenarios/`) with `RoomData` entries (`data/rooms/`). `MapGenerator.generate(scenario, seed, weight_modifiers)` returns a pure-data `MapLayout`; `Level` turns it into rooms, corridors, enemies and the player. Same seed = same map. The director steers rooms only through `weight_modifiers` (room tag -> multiplier) and rooms emit `Events.room_entered/exited/cleared`. The grid is per scenario: `ScenarioData.cell_tiles` (default 30x18 tiles, even numbers) and `corridor_tiles` (default 3). `Level` centres each room in its cell on whole tiles and a corridor spans the real gap between the two facing doors, so its length varies: use `cell_size()`, `stride()`, `cell_origin(coord)` (top-left of the grid cell), `room_origin(coord)` / `room_size(coord)` / `room_rect(coord)` (the room itself) and `corridor_floor(coord, dir)` (dir RIGHT or DOWN); never assume a fixed cell. `Level.room_fit_problem(room_data)` reports a room larger than its cell or off by an odd number of tiles. `ForestBoundary.generate` takes the level for its geometry.
    - **Rooms**: a room is a scene inheriting `scenes/levels/rooms/room_base.tscn`. Its size is `RoomData.size_tiles` (even numbers, default 30x18 tiles = 480x288 px, the size of the forest and the Ruinas; `Room.setup` takes it, and the doors are the middle 4 cells of each edge for any size). Add obstacles as `StaticBody2D`, keep the center cross (for 30x18: x 208..272, y 112..176; in general the 4 middle columns and rows) free so doors stay reachable (`tests/test_room_designs.gd` checks every room of every scenario with real physics), and use the marker nodes `PlayerSpawn`, `EnemySpawns`, `BossSpawn`, `NpcSpawn`, `ChestSpawn`, `SpecialSpawn`. Then create its `RoomData` `.tres` (see `tools/make_test_data.gd`) and add it to the scenario's `rooms`. Run `tests/test_map_generator.gd` and `tests/test_level_build.gd` after any change.
    - **Skills** (`scripts/skills/`): a skill is a `SkillData` (`data/skills/`) whose behaviour is a `SkillEffect` resource. To add one: subclass `SkillEffect` (override `activate`, return how many enemies were affected), expose its numbers with `@export`, and create the `.tres` (see `tools/make_skill_data.gd`). Do not edit `SkillManager`. Unlock with `player.skills.unlock(skill_data)`. Skills only touch enemies through their public methods (`apply_root`, `apply_slow`, `apply_knockback`, Hurtbox for damage); each cast is published as `Events.skill_used(id, direction, affected)`. Stealth is `player.visibility` (enemies scale their sight by it). A skill's look is data too: `SkillData.zone_frames` (`data/skills/<id>_frames.tres`, built by `tools/make_skill_frames.gd` from the strips `python tools/make_skill_art.py` draws into `assets/sprites/skills/`: `start` once, `loop` while the zone lasts, `end` before it goes; a wave's art travels and turns with the cast) is shown by `SkillZone` instead of its shapes, `SkillData.icon` (24x24) fills the HUD slot, and every cast bursts a ring in the skill's color at Nico's feet and flashes it over him (`GameFeel`, `Player.flash()`, `Tuning.CAST_*`). `tools/snapshot_skills.gd` (needs a window) casts the three in the forest and saves screenshots.
    - **Player profile / AI layer 1** (`scripts/ai/`, autoload `PlayerProfile`): it only listens to `Events` and keeps `user://profile.json` (`"version": 1`). `RunStats` (counters of a run) and `ProfileModel` (scores and learning) are pure logic with no nodes; do not add game dependencies to them. Tuning and the summary texts live in `data/ai/profile_config.tres` (see `tools/make_ai_data.gd`), never in code. The director (layer 2) reads `PlayerProfile.live_scores()` / `live_style()` and must not touch the model or the counters. Saving is disabled in headless mode so tests never touch a real profile. To record a new gameplay fact, add a signal to `Events`, emit it from the gameplay code and count it in `RunStats`.
    - **Director / AI layer 2** (`scripts/ai/`, autoload `Director`): `Director.make_plan()` reads `PlayerProfile.live_scores()` and returns a `DirectorPlan` (stat multipliers, enemy count and weights, room-tag weights, Spanish island line and hints). `DirectorLogic.plan_for(...)` is the pure decision (test it without nodes). The rule table is `data/ai/director_rules.tres` (`DirectorRule` per style, see `tools/make_director_data.gd`): tune the AI there, never in code. `Level` applies the plan (room weights to the generator, count and multipliers to the enemies); no other code may read the profile to alter gameplay. An enemy's id is its scene file name. New enemy behaviour must respect the director's multipliers (`_speed_scale()`, `can_see()`). Order matters: `Events.level_started` is emitted first so the profile learns the previous run before the director plans.
    - **Visual theme / tiles** (`scripts/world/tile_art.gd`, `room_theme.gd`, `room_prop.gd`): the Kenney Roguelike/RPG sheet (CC0, in `assets/tilesets/kenney_roguelike_rpg/`) is the default tileset profile (`data/tilesets/kenney_forest.tres`; `assets/tilesets/forest_tileset.tres` is kept only for painting in the editor). Tiles are referred to by ROLE in `TileArt` (never hardcode `Vector2i(16, 9)` outside a profile); to find more tiles render a labeled preview with `tools/atlas_preview.gd` (needs a window), add a role and map it in the profile (see "Tileset profiles and roles"). A `ScenarioData.theme` (`data/themes/*.tres`) dresses rooms and corridors; collision never depends on it. Rooms are described with `RoomProp` nodes (kind, position, size) so they stay readable in text; forest rooms are generated by `python tools/make_forest_rooms.py`, which validates lanes and spawns (edit the layouts there and regenerate, or edit the scenes by hand and run `tests/test_room_designs.gd`). Every new third-party asset goes in `CREDITS.md` with its license file next to the art. The team's forest art set (`assets/art_forest/`) is sorted in `scripts/world/forest_art.gd` (`ForestArt`): solid bushes, ground plants, big and small rocks, the stump, the wall trees (medium) and the forest trees (medium and large); props pick only from the list that fits them (the folders also hold scraps of grass), bushes, boulders and stumps block only with their base (`ForestArt.footprint`, sizes in `Tuning`) and a bush's picture wanders a little (`BUSH_NUDGE`) so bushes side by side never line up like a hedge. With `RoomTheme.forest_art_details` a room swaps its tufts, pebbles and stumps for that art and its walls (and the corridors' walls) become rows of trees whose crowns touch (`TreeWall`, `WallTrees` in each room): the top wall, which nobody walks behind, is two staggered rows baked into one picture; the sides, the bottom and the corridors are single trees y-sorted with the actors and in the `canopy` group. The deep forest around and between the rooms (`ForestBackdrop`) is the rooms' grass with medium and large trees scattered and painted into 512 px chunks, never reaching over a room or corridor (it is drawn below them); `Level`'s `ForestShade` (one pixel per tile, linear filtering, over every floor and under every actor) darkens the forest's floor and creeps a wobbly tile or two into the clearings, so no straight line marks where a room ends. Values: `BACKDROP_*`, `WALL_TREE_*` and `FOREST_SHADE_*` in `Tuning`. Ponds and bridges use the team's own water art (`scripts/world/water_art.gd`, `WaterArt`, drawn by `python tools/make_water_art.py` into `assets/tilesets/water/`; off with `Tuning.WATER_ART_ENABLED`, then the tileset's pond and planks are used): the ponds of a room and the planks touching them are one body of water, so a pond has no shore where a bridge starts; water is a `TileMapLayer` of animated tiles picked by which neighbours are water (rounded shores, a bank under north shores, foam, ripples, lily pads), and a bridge crosses it west to east with deck, rails, piles and its shade on the water. Collision stays `RoomProp`'s (`tests/test_water.gd`). Values: `WATER_*` and `BRIDGE_*` in `Tuning`. Dirt paths and dirt patches use the team's own earth the same way (`DirtArt`, `python tools/make_dirt_art.py` into `assets/tilesets/dirt/`; `Tuning.DIRT_ART_ENABLED`): a frayed, wandering edge over the grass; `Level._soften_paths` keeps the grass in every path cell and paints the earth on a layer just above (`Paths` in a room, `CorridorPath<n>` in a corridor), and paths and patches are one area (a patch loses its corner cells and gets a bite of grass on a long side, so it never reads as a box). `AreaArt` is the shared autotile logic of both sheets. The camp's campfire (stones, logs, animated flame) and the cut stump with roots and shadow used by `LOGS` props and floor details are drawn by `python tools/make_camp_art.py` (`ForestArt.campfire()`, `ForestArt.stump()`, `Tuning.CAMP_ART_ENABLED`).
    - **Tileset profiles and roles** (`scripts/world/tileset_profile.gd`, guide in `docs/GUIA_TILESET.md`): a `TilesetProfile` (`data/tilesets/*.tres`) holds the sheet, its tile size, separation and margin, and maps every ROLE to a tile (`tiles`) or a list of tiles (`patterns`: nine-slice areas of 9, inner corners of 4). `TileArt`'s constants are role names (`TileArt.PINE == &"pine"`), listed in `TileArt.ROLES` and `TileArt.PATTERNS`; code asks the active profile with `TileArt.sprite()`, `tile()`, `coords()`, `pattern()`, `blob_tile()` and `prepare_layer()` (new layers), never with sheet coordinates. A `RoomTheme` names its profile in `tileset` (empty = default) and its tiles as roles; `Level` activates the scenario's profile before building each map. The world grid stays 16 px (`TileArt.TILE`): a pack of another tile size is scaled into it with `Tuning.TILESET_FIT_TO_GRID`. The Ruinas profile (`data/tilesets/ruins.tres`, made by `tools/make_tileset_ruins.gd` from the sheet `assets/tilesets/ruins/ruins_sheet.png` that `tools/make_ruins_tileset_art.py` draws; `tests/test_ruins_tileset.gd`) maps every role to its closest ruins tile (a tall "pine" is a rock column, "grass" is the stone floor, a "pond" is the river) and also keeps every tile of the sheet under its own name (`floor_rune`, `stairs_steps`, `column_tall_a_top`, `crystal_top`, `waterfall_mid_a`...) for the ruins' own props. A new role must be added to `TileArt.ROLES`/`PATTERNS` and to every profile (`tools/make_tileset_profile.gd`); `tests/test_tileset_profile.gd` checks profiles, and `tools/dump_tiles.gd` hashes what a map draws to prove a lookup change keeps the game identical.
    - **Rock walls** (`scripts/world/rock_wall.gd`, `rock_backdrop.gd`, `RoomTheme.wall_style`, `data/themes/ruins.tres`, `tests/test_rock_wall.gd`): a theme with `wall_style = ROCKS` (the Ruinas) draws the walls of rooms and corridors as staggered clusters of the profile's rock columns (`RockWall`, same y-sort and canopy fade as the forest's trees; the top wall is baked into one picture) and fills the space around the map with solid rock (`RockBackdrop`) instead of the forest backdrop and boundary. Sizes and spacing are in `Tuning` (`ROCK_WALL_*`).
    - **Room plans** (`scripts/world/ruin_shape.gd`, `ruin_anim.gd`, `tests/test_ruin_shape.gd`): a room of the Ruinas is an irregular cave, not a rectangle. Its `Shape` node (`RuinShape`) holds the plan as 18 lines of 30 characters (the Ruinas' rooms are always 30x18; `#` rock, `.` floor, `~` water, `=` planks, `r` bridge parapet, `w` waterfall): rock cells get solid collision (merged rectangles), a mass of rock tiles and columns along their edge; water cells get the river's rounded shore (`TileArt.blob_tile` with the `pond` and `pond_inner` patterns), collision on the water layer and a shimmer of three center frames; border walls the rock leans on are not drawn (`hides_wall_at`), so the outline has no straight line. The plans are drawn by `tools/make_ruins_rooms.py` (blobs of rock bitten out of the rectangle, winding rivers straight at the bridge, pools under waterfalls) and can be edited by hand. A corridor between rooms of different height is a staircase between two stone parapets with a torch at its top.
    - **Ruins scenario** (`data/scenarios/ruins.tres`, `scenes/levels/ruins_level.tscn`, `tests/test_ruins.gd`): 10 room designs (start, boss, river, terraces, plateau, narrow, falls, event, reward, special) generated by `python tools/make_ruins_rooms.py` (it validates lanes, spawns and the free tiles in front of every staircase, and adds rock outcrops that bite into the room from its walls, so no floor is a plain rectangle; the narrow and falls rooms carry spike traps, `RuinProp.Kind.SPIKES`) and turned into `RoomData` and the scenario by `tools/make_ruins_data.gd` (the boss arena and the plateau are raised). Regenerate in this order: art (`tools/make_ruins_tileset_art.py`), profile (`tools/make_tileset_ruins.gd`), theme (`tools/make_ruins_theme.gd`), rooms, data. Its enemies are the old Bestia de la niebla, Sombra errante and Murciélago; the forest's exit already leads to it (`forest.tres` `next_scenario`, `tests/test_chapters.gd`) and its own exit leads to the temple; the Viajera waits in its event room (`scenes/npcs/traveler.tscn`, `data/dialogues/traveler.json`, speaker colors in `data/ui/dialogue_speakers.json`); its boss is the Serpiente de piedra (`scripts/enemies/stone_serpent.gd`, `data/enemies/stone_serpent.tres`, `tests/test_serpent.gd`): its portal stays sealed until `ruins_boss_defeated`, then the blue fragment teaches Corriente and the exit leads to the temple.
    - **Temple scenario** (`data/scenarios/temple.tres`, `scenes/levels/temple_level.tscn`, `tests/test_temple.gd`): 13 room designs (start, boss, pillar_court, isles, terraces, trap_walk, lava_falls, surge_basin, surge_tiers, surge_bridges, sanctum, event, special) in three sizes (`RoomData.size_tiles`, per `docs/superpowers/specs/2026-11-07-templo-escala-design.md`): large 42x28 (boss, pillar_court, surge_tiers, surge_bridges), medium 34x24 (start, isles, terraces, trap_walk, lava_falls, surge_basin) and small 26x20 (sanctum, event, special), each centred in the scenario's 48x32 grid cell (`cell_tiles`; `corridor_tiles` stays 3, so a corridor is the real gap between two doors, 6x4 tiles between two large rooms and up to 22x12 between two small ones). Each is a `TempleShape` island over lava composed like `docs/referencias/templo_mapa.jpg`: wide organic outlines on thick cliffs, up to three height levels with clear flights of stairs, isles reached only by a bridge (the sanctum's chest, the isles' altar and east isle, the surge bridges' ring), masonry ridges with lava falls, and one focal piece per room on the axis of its door (the face gate up a wide stair, the altar on the court's dais, the ziggurat's top) framed by mirrored pairs of pillars, braziers or statues (`TempleProp`); few props (no posts on the shores, no urns, vines and moss only on the cliffs, hazard geysers and traps in the trap walk) and generous open floor for the fights. The plans are hand-drawn in `python tools/make_temple_rooms.py` (the plan's size is the room's), which never ports the rules: it hands every plan to Godot (`tools/validate_temple_plans.gd`, `TemplePlan.validate` with the room's surge stages and base height, `spawn_ok` and the reached cells) and refuses to write a room with a problem, a solid prop off the floor of its level or on a lane (base-height props only; the boss's face gate stands on the north lane, which a boss cell never opens), or a marker off a `spawn_ok` cell; it then picks the enemy spawns among the `spawn_ok` cells (a surge room's on its safe level). `tools/make_temple_data.gd` checks the scenes again the same way (the plan's size against the room's `size_tiles` too) and writes the `RoomData` (size; tags `court`, `bridges`, `heights`, `traps`, `falls`, `surge`; `enemy_affinity` per room; the surge rooms' `Surge` group, weight 2) and the scenario (grid 5x5 with a main path of 6 to 9 rooms, `cell_tiles` 48x32, 24 of the temple enemies (the bridge worm, `gusano_puentes`, is left out of the pool: too hard in playtests), `roster_size` 10, the Guardián antiguo, `temple_boss_defeated`), and points `ruins.tres` at it: the temple is the last chapter and ends the journey (`tests/test_ending.gd`). Regenerate rooms, then data. `Level._populate` attaches the `LavaSurge` of a surge room (with the map seed, the director's plan and the room's weights) and spawns its own enemies only on `safe_spawn_cells()`; every enemy takes the level of the cell it is born on; a corridor between rooms two levels apart is an error, never a staircase. The director's rule table weighs the temple tags too (`tools/make_director_data.gd`). `tools/snapshot_temple.gd` (needs a window) saves a screenshot of every room (at its own size) on lava and one overview of a whole map to compare with `docs/referencias/templo_mapa.jpg`. A temple map builds in about 2.5-3 s (`tests/test_temple.gd` prints it); the cost is per cell in `TempleShape._build_ledges` (a blob mask per cell) and `_build_collision` (`TemplePlan.collision_rects` for six layers).
    - **Temple room plans** (`scripts/world/temple_plan.gd`, `temple_shape.gd`, `tests/test_temple_plan.gd`, `tests/test_temple_shape.gd`): a plan is a grid of characters whose size comes from its text: any number of rows, all of one length, both even and at least 8 (`columns`, `rows`, `size_cells()`; 18x30 is only the default), and it must equal its room's `RoomData.size_tiles` (`TempleShape` adds an error to `plan.errors` and builds nothing otherwise, `TempleShape.size_problem`). The temple's rooms are 42x28, 34x24 and 26x20 (see "Temple scenario"); the Ruinas' and the forest's stay 30x18. Cells: `.`, `1`, `2` floor at height 0, 1, 2; `~` lava (-1); `^ > < v` a stair climbing toward the arrow (its own cell is the low end); `=` and `|` a deck at 0 (west-east, north-south); `b` and `B` a raised deck at 1 and 2; `#` masonry; `p` a pillar slot (floor of its west neighbour's height, its prop brings the body). The outer ring is masonry except the 4 middle cells of each edge, the doors, which share one base height.
      - Faces: a cell south of a cell `d` levels higher shows `d` rows of cliff (`face_rows`) and is not walkable at its own height; stairs and decks never show one. Collision layers: 1 masonry, 7 lava, 8 what level 0 may not enter (raised cells and faces), 9 what level 1 may not enter, 10 what level 2 may not enter, 11 the height-2 cells. `collision_rects(layer)` merges each into rectangles; a raised deck blocks only at its two ends.
      - `TemplePlan.validate(surge_stages)` returns the problems: the doors reach each other at base height, every walkable cell is reached (BFS over cell and level, through stairs), each stair has a free cell at both ends, the floor is not a plain rectangle (at least 20% of the inner cells, measured over the plan's own inner area, are not base floor), the center lanes (the 4 middle columns and rows, `lane_first_column()`, `lane_first_row()`) are not cut and, for a surge room, every level-0 cell is near a stair up and the safe level has 60 connected cells. `spawn_ok(cell)` is an inner cell reached at its own height, not a face or stair, with no lava among its 8 neighbours; `level_regions()` gives the reached inner cells of each level, `stairs()` the `StairZone` rectangles.
      - `TempleShape` (the room's `Shape` node) paints tile layers, bottom to top: Lava (at `LavaBackdrop.SEA_Z`), Bubbles, Faces, Floor0 to Floor2 (macro slabs of each level), FloorDetail, Rims and RimGlow (`TileArt.blob47_tile(&"lava_rim")`), Ledges (`blob47_tile(&"ledge")`, a 3 px lit lip), Shadows (cast south) and ShadowsEast (cast east), Stairs (pale steps with a balustrade on the open sides of a flight), Bridges; rails, posts and the braziers or posts marking the top corners of every flight are sprites y-sorted with the actors.     - **Lava surge** (`scripts/world/lava_surge.gd`, `lava_surge_logic.gd`, `tests/test_lava_surge.gd`): `LavaSurgeLogic` (pure) runs IDLE, WARNING (`TEMPLE_SURGE_WARN_SECONDS`), RISING (`RISE_SECONDS`), FIGHT; with two stages, `kills_stage_1` kills warn again and the lava rises to stage 2, and `kills_to_recede` kills in the last stage make it RECEDE one level at a time (`RECEDE_SECONDS` each) until DONE. Flyers (`Heights.is_flyer`) and bodies without a Hurtbox are exempt. A kill by lava does not count (`_lava_victims`; a survivor counts again).

Failsafes: the fight ends at once with an empty roster or, with nothing alive or coming, after `STALL_INTERVALS` (3) wave intervals without a free cell; a room cleared before Nico steps in is never sealed.

## Art and assets
21. Characters are made by the team in **Pixelorama**: 32x32 sprites for Nico and small enemies (bosses, big enemies and NPCs may be 64x64), one shared palette of 16–24 colors, minimum animations idle / walk / attack / hurt / die. Views: Nico has 3 (front, back, side) + flip; enemies and bosses one side + flip; NPCs front only. Animations are found by name, `<animation>_<view>` with the views `down` (front), `up` (back) and `side` (facing right): Nico's art is the strips `assets/sprites/nico/nico_<animation>_<view>.png` read by `tools/make_nico_frames.gd` (`idle`/`walk` in the 3 views; `attack`, `hurt`, `death`, `dash` side only). A missing view falls back to `<animation>_side`.
22. Tilesets are 16x16 (a free pack may be used; record it in `CREDITS.md`). Every third-party asset must be listed in `CREDITS.md` **in the same commit** that adds it, with its license.
23. Keep source art (`.pxo`) next to exported PNGs under `assets/sprites/<name>/`.
